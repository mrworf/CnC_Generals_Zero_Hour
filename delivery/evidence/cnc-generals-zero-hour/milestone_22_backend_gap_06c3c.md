# M22 06C3C renderer-backend capability escalation (section 9)

Status: **unresolved implementation blocker; no backend selection or reduced acceptance**. Accepted through 06C3B3B (`4f9b286`) remains valid. This is the first required original scene clear inside an already active frame, not a performance preference or driver failure.

## Exact source consumer and expected result

Original `WW3D::Begin_Render` opens a frame, then [`WW3D::Render(SceneClass*,CameraClass*,...)`](../../../GeneralsMD/Code/Libraries/Source/WWVegas/WW3D2/ww3d.cpp) calls `cam->Apply()` and, if requested, `DX8Wrapper::Clear(clear,clearz,color)` **before** `scene->Render(rinfo)` and `Flush(rinfo)`. The original [`CameraClass::Apply`](../../../GeneralsMD/Code/Libraries/Source/WWVegas/WW3D2/camera.cpp) selects the camera's subrect viewport and depth range. Original [`DX8Wrapper::Clear`](../../../GeneralsMD/Code/Libraries/Source/WWVegas/WW3D2/dx8wrapper.cpp) issues D3D8 `Clear(0,NULL,flags,...)` with independent color and depth/stencil flags. [Microsoft's D3D8 Clear contract](https://learn.microsoft.com/en-us/previous-versions/ms889282%28v%3Dmsdn.10%29) states that `NULL` clears **the viewport rectangle**, with rectangle coordinates clipped to the viewport. A camera inset in a frame that already drew its outer area must therefore clear only the inset's color/depth/stencil and retain everything outside it; another scene can be rendered later in the same frame before the original `End_Render`/presentation.

## Minimal reproducer / failed public capability

Given a 160×120 RGBA/depth-stencil target, original frame Begin clears it red/depth 0.25. Camera `Viewport.Min=(0.25,0.25)`, `Max=(0.75,0.75)` selects x=40..119, y=30..89. `WW3D::Render(scene,&camera,true,true,blue)` must leave the outer pixels red/depth 0.25 and set only this camera rectangle blue/depth 1/stencil 0, before drawing the scene; then End presents one ordered frame. This is a bounded fixture for the future backend, not a generated positive scene substitute.

Installed SDL3 3.4.14 `/usr/include/SDL3/SDL_gpu.h` exposes `SDL_BeginGPURenderPass` load/clear **only at pass start**, `SDL_SetGPUViewport`, and `SDL_SetGPUScissor` for draws; no public active-pass rectangle clear command exists. [SDL's BeginGPURenderPass documentation](https://wiki.libsdl.org/SDL3/SDL_BeginGPURenderPass) states CLEAR initializes the **entire texture subresource before rendering**, that another pass cannot begin until End, and that pass end resets render-related state. [SDL's blit documentation](https://wiki.libsdl.org/SDL3/SDL_BlitGPUTexture) disallows blits inside a pass and does not provide simultaneous color/depth/stencil viewport clearing. Current [`SdlGpuDevice::begin_pass`](../../../src/renderer/sdl_gpu_device.cpp) maps CLEAR to attachment load operations and rejects nested passes; `set_viewport` only calls `SDL_SetGPUViewport`. Merely setting the viewport before an attachment CLEAR therefore clears the full target. Ending/reopening with CLEAR loses outer pixels, while a LOAD restart has no public rectangle clear and resets source-selected pipeline/bindings. A shader-drawn rectangle would invent clear geometry/pipeline and is excluded by this milestone's no-proxy source-authority boundary and the parent's device-edge guardrail. A private Vulkan call below SDL_GPU is explicitly forbidden by section 9.

## Decision gate

The port plan [section 9](../../../docs/zero-hour-linux-port-plan.md) requires a recorded choice: demonstrate a public abstraction that passes the exact original viewport color/depth/stencil and interleaved ordering repro, or replace the backend layer with bgfx if it does; if both abstractions fail, explicitly budget raw Vulkan. [bgfx's public `setViewRect` and `setViewClear`](https://bkaradzic.github.io/bgfx/bgfx.html) make it a **candidate**, not yet proof: the exact per-view rectangle/depth/stencil preservation, ordered multiple source scene clears within a frame, and accepted W3D render categories still require an executable spike. No new library/backend has been installed, selected or committed. Do not mark 06C3C, 06C4, 07–09 or M22 accepted on full-target-only frame evidence. A decision/replan should supply a tested replacement backend contract, migration scope and revalidation of M7–M10/M14/M22 before delivery resumes.

No private retail files were read, copied or modified while establishing this API/source gap. There are no scene pixels falsely counted as positive acceptance; existing B3B explicit-validation Vulkan evidence remains separate.
